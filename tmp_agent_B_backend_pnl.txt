# P&L Recording Pipeline Audit — Complete Findings

## Pipeline Architecture Map

The intended flow is:

```
CT order placed (201) 
  -> FillsPoller (HTTP, 20s) / WsBridge (WS, near-real-time)
    -> KalshiFillsLedger.ingest_*
      -> fill_bus publish "kalshi:order_filled"
        -> [no APT subscriber — social only]
      -> AgentPerformanceTracker.record_fill()  [called directly in CT]
  
Market settles
  -> reconciliation.py: _reconcile_kalshi_venue -> _fire_settlement_hooks
    -> AgentPerformanceTracker.record_outcome()  [closes open trade, computes P&L]
  -> OutcomeResolver.resolve_all() -> _notify_bankroll_of_settlement()
    -> KalshiRiskEngine.record_trade_result()  [updates CT bankroll P&L]
```

## BUG 1 — OutcomeResolver is Never Started as a Background Task

**File:line:** `web/main.py` — no call to `resolver.start()` anywhere  
`merid/metrics/outcome_resolver.py:431` — `start()` method exists but is never invoked

**What's broken:** `OutcomeResolver.resolve_all()` is the only path that calls `_notify_bankroll_of_settlement()` (line 220 of `outcome_resolver.py`), which in turn calls `engine.record_trade_result(pnl_cents)` (line 282) to update `KalshiRiskEngine._total_pnl_cents`. The resolver is only accessible via the metrics API endpoints (`POST /api/v1/kalshi/metrics/resolve-all`, etc.) — manual operator trigger only. There is no background task running it on a schedule. The comment at `kalshi_continuous_trader.py:3251-3252` explicitly says "PnL is deferred to settlement — OutcomeResolver calls bankroll.record_trade_result()" but the OutcomeResolver never runs automatically.

**Fix:** In `web/main.py` startup (lifespan), after the FillsPoller starts, add:
```python
from merid.metrics.outcome_resolver import get_outcome_resolver
_outcome_resolver = get_outcome_resolver()
await _outcome_resolver.start(interval_s=300)
```
And add a teardown call `await _outcome_resolver.stop()`.

## BUG 2 — CT Never Calls `edge_store.record_trade_entry()` — OutcomeResolver Has Nothing to Resolve

**File:line:** `merid/trading/kalshi_continuous_trader.py:3253` — `self.bankroll.record_trade_entry()` (KalshiRiskEngine method, increments trade count only)  
`merid/metrics/outcome_resolver.py:138` — `edge_markets = set(self._edge_store.get_unresolved_markets())`

**What's broken:** `OutcomeResolver.resolve_all()` (line 138-139) gets the list of markets to check from `self._edge_store.get_unresolved_markets()`. The `RealizedEdgeStore` only knows about a market if `record_trade_entry()` was called on it at fill time. CT calls `self.bankroll.record_trade_entry()` (the KalshiRiskEngine method at line 682), which only increments a counter. CT never calls `get_realized_edge_store().record_trade_entry(trade_id, forecaster_id, bucket, market_id, ...)`. Therefore the edge store is always empty, `get_unresolved_markets()` always returns `[]`, and `OutcomeResolver` never processes any trade, so `_notify_bankroll_of_settlement()` is never triggered even if the resolver were started.

**Fix:** In `kalshi_continuous_trader.py`, after the HTTP 201 order accept block (around line 3253), add a call to `get_realized_edge_store().record_trade_entry(...)` passing the order_id, a forecaster_id string (e.g., `f"kalshi_ct_{self.asset_symbol}"` ), bucket (`"crypto"`), `c.ticker`, `c.best_side`, `c.limit_price_cents`, a model prob, implied prob, `order_count`, and the fee.

## BUG 3 — CT Exit Block Does Not Record Close in `AgentPerformanceTracker`

**File:line:** `merid/trading/kalshi_continuous_trader.py:2159-2186` — `_submit_sell_yes_limit()` call, no `_apt.record_close()` after successful exit  
`merid/trading/kalshi_continuous_trader.py:1440-1450` — `_submit_sell_yes_limit` inner block only calls `self._notifier.record_fill()`

**What's broken:** When a position is closed via stop-loss or profit-take (`exit_reason` set and `_auto_exit_enabled()`), `_submit_sell_yes_limit()` is called. On success (201), it calls `self.tracker.record_order()` and `self._notifier.record_fill()`. It does NOT call `AgentPerformanceTracker.record_close()`. This means the close is never registered, `_open_trades` leaks the entry forever, `total_closes` stays zero, `wins`/`losses` are never recorded, and `total_pnl_usd` never updates in `AgentPerformanceTracker`.

The P&L for an exit trade is computable at exit time: `pnl = (exit_price - entry_price) * contracts`. The entry price is in `_open_trades[f"{agent_id}:{market_id}"].entry_price_cents`.

**Fix:** After a successful `_submit_sell_yes_limit()` call in the exit block (line 2159), call:
```python
try:
    _apt = get_agent_performance_tracker()
    _agent_key = f"kalshi_ct_{self.asset_symbol.lower()}"
    _entry = _apt._open_trades.get(f"{_agent_key}:{ticker}")
    if _entry:
        _pnl_cents = (limit_cents - _entry.entry_price_cents) * qty
        _apt.record_close(_agent_key, ticker, limit_cents, Decimal(str(_pnl_cents / 100)))
except Exception: pass
```

## BUG 4 — `_build_agent_map()` in FillsPoller Always Returns Empty Dict

**File:line:** `merid/event_venues/kalshi/fills_poller.py:434-451`

**What's broken:** `_build_agent_map()` tries to get `agent.state.pending_orders` from each agent in the grid. CT-placed orders are NOT routed through the agent grid — CT is a standalone class that places orders directly. The `agent_map` is always `{}` for CT fills. This means fills ingested by the HTTP poller have `agent_id = None` (unless an intent was registered). CT never calls `ledger.record_intent()` either (confirmed by grep — no `record_intent` calls in `kalshi_continuous_trader.py`). Therefore all CT fills arrive in the ledger with `fill.agent_id = None`, and the `summary()` PnL aggregation cannot break down by agent.

**Fix (minor):** Either (a) register an `OrderIntent` in the ledger at CT fill time using the `client_order_id`, or (b) have `_build_agent_map()` also scan `LiveOpenOrderRegistry` which does have CT orders registered.

## BUG 5 — `KalshiFillsLedger.summary()` PnL Calculation Is Systematically Wrong for Binary Contracts

**File:line:** `merid/event_venues/kalshi/fills_ledger.py:749-755`

**What's broken:** The summary computes realized P&L as:
```python
sign = Decimal("1") if fill.action == "sell" else Decimal("-1")
pnl_contribution = sign * fill.notional_usd - fill.fee_cost
```
This treats a fill as "realized" at the time of each fill, not at settlement. For Kalshi binary contracts, a buy fill at 45¢ is NOT a loss of 45¢ — it's a position that will either pay 100¢ or 0¢ at settlement. The "realized" P&L for a buy fill is -cost (capital at risk), and the realized P&L for a sell fill is +proceeds. This means `daily_realized_pnl_usd` and `total_realized_pnl_usd` returned by `GET /api/v1/kalshi/risk` are mark-to-fill-price approximations, not true settled P&L. All open positions show a constant negative P&L equal to their entry cost, which is mathematically wrong.

**Fix:** The ledger `summary()` should only count `action == "sell"` fills as realized revenue and pair them against matched buy fills. More correctly, use `compute_net_positions()` to identify closed positions (where buy qty equals sell qty for a market) and compute P&L only on those. Or leave the ledger P&L as-is and clearly document it as "cost-basis" not "settled P&L" — the real settled P&L must come from `OutcomeResolver`.

## BUG 6 — `_fire_settlement_hooks()` Is Called From a Sync Context That Cannot Fetch Kalshi API

**File:line:** `merid/reconciliation.py:353-357` — `_fetch_kalshi_settlement()` returns `None` if a running event loop is detected  
`merid/reconciliation.py:297-305` — `_fire_settlement_hooks()` called synchronously from `_reconcile_kalshi_venue()`

**What's broken:** `_reconcile_kalshi_venue()` is called via `await asyncio.get_event_loop().run_in_executor(None, lambda: reconcile_all_venues(["kalshi"]))` in `web/main.py` (line 3212). This runs in a thread pool, but the async event loop is still running. When `_fetch_kalshi_settlement()` is called from that thread, it checks for a running loop and returns `None` (line 353-357). This means settlement hooks always fall back to inferring `settled_yes` from the position side (line 389), which is always `True` for YES positions. All YES positions are incorrectly assumed to have settled YES.

**Fix:** `_fire_settlement_hooks()` should accept `settled_yes` as an optional parameter, or be deferred to the async context. Alternatively, pass the settled outcome from `_reconcile_kalshi_venue()` where it has it from the Kalshi positions API (a zero-quantity position indicates settlement but not direction — this is a hard limitation). The correct fix is to call the Kalshi `get_market()` API asynchronously within the async reconcile context before dispatching to the thread.

## BUG 7 — SettlementPoller Has No Callback Wired to `AgentPerformanceTracker` or `OutcomeResolver`

**File:line:** `web/main.py:2595-2605` — `start_settlement_polling_auto()` called with no grading_callback  
`merid/event_venues/kalshi/settlement_poller.py:1139-1149` — `start_settlement_polling_auto()` never calls `get_settlement_bridge()`

**What's broken:** The `KalshiSettlementPoller` is started in `web/main.py` but no callback is registered on it. The `SettlementToGradingBridge` class exists at `settlement_poller.py:1031` but `get_settlement_bridge()` is only referenced in `merid/prediction/pipeline_integration.py` — and `initialize_pipeline_integration()` is never called from `web/main.py`. So when a market settles and the poller fires its callbacks, zero callbacks are registered, and no downstream P&L accounting happens from the settlement poller path.

**Fix:** In `web/main.py` startup, after starting the settlement poller, create the bridge with a grading callback that calls `AgentPerformanceTracker.record_outcome()` and/or triggers `OutcomeResolver.resolve_all()`.

## BUG 8 — `GET /api/v1/kalshi/risk` `realized_pnl_usd` Will Show Zero for All Open Positions

**File:line:** `web/api/kalshi_api.py:3519-3533`

**What's broken:** The `/risk` endpoint uses `ledger.summary()` for its canonical `realized_pnl_usd`. As established in BUG 5, the ledger `summary()` only counts `action == "sell"` fills as positive P&L. Since CT only places buy orders (all orders have `"action": "buy"` in `order_data`), all fills land as `action = "buy"` after HTTP ingestion (line 874: `if source != "websocket" and _count_fp > 0: _action = "buy"`). There will never be any `action == "sell"` fills from CT buys, so `total_realized_pnl_usd` is permanently `-(sum of all buy notionals)`. Exit trades placed via `_submit_sell_yes_limit` may produce `action = "sell"` fills when polled, but those are not matched against entries in the ledger formula.

**Fix:** This is consequential of BUG 5. The `/risk` endpoint's `realized_pnl_usd` is structurally unreliable as a P&L metric. The true realized P&L path is through `OutcomeResolver` -> `KalshiRiskEngine.total_pnl_cents`. The API should expose `ct.bankroll.total_pnl_cents` as the authoritative realized P&L once BUGs 1 and 2 are fixed.

## BUG 9 — `GET /api/v1/kalshi/pnl` Returns Zero `total_pnl_usd` Until APT Has Closed Trades

**File:line:** `web/api/kalshi_api.py:3413-3444`

**What's broken:** This endpoint iterates `AgentPerformanceTracker.get_all_metrics()` and sums `m.total_pnl_usd`. Since `record_close()` is never called for CT exits (BUG 3) and settlement hooks do call `record_outcome()` but only work if there's an open trade in `_open_trades` (which requires `record_fill()` to have been called first), the only fills that feed APT are CT buys. `total_pnl_usd` in APT only accumulates when `record_close()` is called, which requires an active `_open_trades` entry. If exit trades don't call `record_close()`, this endpoint returns zero P&L permanently.

**Fix:** Fix BUG 3. Also note: `daily_pnl_usd` is not tracked here — this endpoint has no time-bucketed P&L.

## BUG 10 — `reconcile_all_venues()` Defaults to `["alpaca"]` if `paper_config` Import Fails

**File:line:** `merid/reconciliation.py:509-515`

**What's broken:** The fallback venues list is `["alpaca"]`, not `["kalshi"]`. If `get_paper_config()` raises any import error (likely given Alpaca is a dead module), `reconcile_all_venues()` silently runs against "alpaca" (which has no adapter and returns zero discrepancies), never running `_reconcile_kalshi_venue()`. In `web/main.py` line 3291, the explicit call passes `["kalshi"]` — but the startup reconciliation at line 3212 calls `lambda: reconcile_all_venues(["kalshi"])` with explicit arg, so this specific path is safe. The background thread at line 3291 also passes `["kalshi"]`. However, any call to `reconcile_all_venues()` without arguments (e.g., from operator scripts or tests) silently misses Kalshi.

**Fix:** Change the fallback from `["alpaca"]` to `["kalshi"]` at line 513.

**Issue 1 — Paper mode POST /orders returns a hardcoded stub fill** (`kalshi_api.py:2799`): When `order_router` is unavailable AND mode is "paper", the fallback at line 2799 returns `{"fill": {"price": price_cents, "count": count, "simulated": True}}` — no fill ID, no ledger write, no persistence. This is intentional paper behavior but means paper fills never reach `KalshiFillsLedger`.

**Issue 2 — Portfolio endpoints require `KalshiVenueClient`** (`kalshi_api.py:2273, 2314, 2351, 2389, 2426, 2466`): `/portfolio/summary`, `/portfolio/risk`, `/portfolio/var`, `/portfolio/pnl`, `/portfolio/subaccounts`, `/portfolio/history` all call `_get_client()` and raise HTTP 503 if it returns None. `_get_client()` requires `KALSHI_API_KEY_ID` + `KALSHI_PRIVATE_KEY_PATH` to be configured and not equal to `"change_me"`. If credentials are absent, these six endpoints are permanently broken with 503.

**Issue 3 — Orderbook endpoint silently empties** (`kalshi_api.py:886`): If both the venue client and rest_client are None, it returns `{"yes_bids": [], "yes_asks": [], ..., "error": "No Kalshi client configured"}` with HTTP 200, not 503. The frontend will silently receive an empty orderbook.

### 7. Orderbook Endpoints

All orderbook data comes from real Kalshi sources — no local MatchingEngine is used for orderbook display:

- `GET /api/v1/kalshi/markets/{ticker}/orderbook` (`kalshi_api.py:807`) — tries `KalshiVenueClient.get_orderbook()` first, then `rest_client.get_orderbook()`. The MatchingEngine (`merid/matching_engine.py`) is used only for paper order execution, not for orderbook display.
- `GET /api/v1/kalshi/markets/{ticker}/orderbook/stream` (`kalshi_api.py:576`) — opens a live `KalshiWebSocket` connection per request, subscribes to `orderbook_snapshot` + `orderbook_delta` channels, and streams via SSE. This creates a new WS connection per client HTTP request, which could be expensive under load.

**Issue 6 — `/orderbook/stream` creates a new KalshiWebSocket per HTTP request** (`kalshi_api.py:604`): Each SSE client spins up its own `KalshiWebSocket()` and calls `ws.connect()` + `ws.subscribe_orderbook(ticker)`. If 10 clients request the same ticker, 10 separate WS connections are opened to Kalshi. The existing `ws_bridge` which already subscribes to tickers is not reused here.

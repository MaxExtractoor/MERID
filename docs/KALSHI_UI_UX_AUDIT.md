# MERID × Kalshi UI/UX Audit (2026-03-26)

Scope: React front-end views/components under `web/react/src/**` that surface Kalshi state. Focused on wiring errors, duplicated logic, dead props, orphaned elements, and lifecycle alignment.

## Baseline
- Tests: `pytest tests/test_bugfix_regressions.py tests/event_venues/kalshi/test_kalshi_regression.py` (dockerized Python 3.11) → **failed** because pytest is invoked with `--checklist-collect/--checklist-report` options that are not recognized by the installed plugins (mirrors CI failure in run 23567594881).

## Findings
| Component & Path | Severity | Issue Summary | Root Cause | Suggested Fix | Lifecycle Alignment |
| --- | --- | --- | --- | --- | --- |
| KalshiDashboardView (`web/react/src/views/KalshiDashboardView.tsx`) | High | Every market card renders `OrderbookPanel`, which instantiates its own `useApiData` with FAST polling. With the default 200-market limit, this spawns hundreds of overlapping `/api/v1/kalshi/markets/{ticker}/orderbook` polls, risking rate-limit trips and UI stalls. | `showOrderbook` defaults to true and the `OrderbookPanel` is created inside the map without pagination/virtualization or shared orderbook feed. | Gate orderbook polling behind explicit “peek orderbook” toggle per card, or centralize a single orderbook stream keyed to the selected market. Reduce default list limit or virtualize the grid to avoid fan-out. | Breaks Protect/Monitor: overloads venue and obscures real-time accuracy when the swarm should be monitoring. |
| KalshiPortfolioView (`web/react/src/views/KalshiPortfolioView.tsx`) | High | Trade/kill-switch actions stay enabled even when the session is blocked or kill switch is active; `sessionOpen`/`kill_switch_active` are only shown as badges, not enforced on buttons (downsize, amend, cancel). Operators can route actions while trading is disallowed. | Session/kill state is read (`sessionResult`, `ksResult`, `gridPortfolioResult`) but never used to disable action handlers. | Disable/gray actionable buttons when `!sessionOpen` or kill flags are true; surface inline reason and require acknowledgement before re-enabling. Propagate the guard into `handleDownsize`, amend, cancel, and batch-cancel paths. | Violates Protect/Execute: actions bypass guardrails. |
| KalshiPortfolioView (`web/react/src/views/KalshiPortfolioView.tsx`) | Medium | “Cancel all orders” confirmation uses the **filtered** order count (per asset) but sends a global `/api/v1/kalshi/orders` DELETE, cancelling unrelated orders. UI misleads operators. | Confirmation text derives from `orders.length` (filtered) while the endpoint cancels every open order. | Add scope-aware cancel (per asset filter) or make confirmation and endpoint both global; show the real global count and require a second confirmation if filters are active. | Misaligned Size/Protect: operator intent is not reflected in backend action. |
| KalshiDashboardView (`web/react/src/views/KalshiDashboardView.tsx`) | Medium | Markets endpoint is polled twice concurrently (`marketsEndpoint` and `limit=500` unfiltered) even when the positions sidebar is hidden or no positions exist, doubling catalog traffic. | Separate `useApiData` instances for filtered markets and “all markets” are always active; sidebar visibility/position count are not used to gate the second poll. | Only fetch the unfiltered list when the positions sidebar is visible and `positionTickers.size > 0`, or reuse the filtered payload for sidebar rendering. | Inefficient Monitor/Discover; wastes bandwidth and risks stale data. |
| KalshiVolDashboardView (`web/react/src/views/KalshiVolDashboardView.tsx`) | Medium | Mode toggle to LIVE ignores kill-switch state and catalog/risk degradation; operators can flip to LIVE while `killActive` is true or venue health is degraded. | `handleModeToggle` checks only `liveEnabled` and the current `isLive` flag; it does not consult `killRes`, `risk` or `health.status` before POSTing. | Block or require override when kill switch is active, health is degraded/down, or rate limits are near saturation; surface the block reason inline. | Protect/Execute misalignment; allows unsafe promotion. |
| KalshiSentimentView (`web/react/src/views/KalshiSentimentView.tsx`) | Low | Swarm sentiment panel renders an amber “unavailable” banner whenever `SENTIMENT_ASSETS_ALL` is empty, even if `SENTIMENT_HASHTAG_SIGNALS` returns live signals. Signals tab becomes orphaned and invisible in that state. | Rendering gate is tied only to the assets payload; signals are fetched independently but never shown when assets array is empty. | Allow the signals table to render when signals arrive even if assets payload is empty; add a stub row explaining missing asset context instead of hiding the panel. | Promote/Analyze: insight surfacing is blocked despite available data. |

## Lifecycle Coverage Snapshot
- **Kalshi Dashboard**: Discover/Analyze/Size present; Execute/Monitor present via ticket + book overlays; Protect weakened by uncontrolled per-card orderbook fan-out.
- **Kalshi Portfolio**: Monitor/Execute/Protect intended but Protect enforcement is missing (actions ignore kill/session); Size alignment via sizing metrics is intact.
- **Kalshi Grid**: Consensus/Execute/Monitor covered; Protect depends on external kill switch but not enforced in UI actions.
- **Kalshi Vol Dashboard**: Protect/Monitor/Size presented, but mode switching bypasses Protect checks.
- **Kalshi Sentiment**: Discover/Promote paths present; partial Monitor due to gating gap above.

Please confirm whether to prioritize Protect-stage guardrails or optimize the dashboard poll patterns first; both touch shared hooks (`useApiData`) and operator workflows.

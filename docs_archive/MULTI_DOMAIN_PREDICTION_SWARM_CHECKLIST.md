# Multi-Domain Prediction Swarm Must-Have Checklist (Crypto, Stocks, Betting)

> **Purpose**: Verify MERID has all must-haves for multi-domain predictions across crypto, stocks, and prediction/betting markets using an AI swarm architecture.  
> **Scope**: Concrete, testable checkboxes for a small team to implement iteratively.

---

## 1. Data & Features Layer

### 1.1 Unified, Low-Latency Feeds

- [ ] **Crypto feeds**: WebSocket connections to ≥2 exchanges (e.g., Kraken, Coinbase) with <500ms tick-to-ingest latency; monitored via `prices.spot.*` topic throughput
- [ ] **Stock feeds**: Real-time quotes via broker API (Alpaca/IBKR) with <1s latency for top 100 symbols; fallback to 15-min delayed if primary fails
- [ ] **Prediction market feeds**: Polling or WebSocket to Kalshi (US-compliant) with contract prices, volumes, and open interest; <5s refresh for active contracts
- [ ] **Feed health dashboard**: Single view showing last-seen timestamp, error rate, and latency p99 per feed; alerts if any feed >30s stale

### 1.2 Normalized Schemas

- [ ] **Price schema**: All domains emit `{symbol, venue, bid, ask, last, volume, timestamp, asset_type}` to `prices.*` topics
- [ ] **Orderbook schema**: L1/L2 snapshots as `{symbol, bids[], asks[], timestamp, depth}` across crypto/stocks/prediction markets
- [ ] **Trade/fill schema**: Executed trades as `{trade_id, symbol, side, qty, price, timestamp, venue}` for audit and P&L
- [ ] **Odds/contract schema**: Prediction markets emit `{contract_id, market_id, yes_price, no_price, volume, open_interest, resolution_source, expiry}`
- [ ] **News/sentiment schema**: Headlines as `{news_id, headline, symbols[], sentiment_score, source, timestamp}`; sentiment as `{symbol, score, mentions, source}`
- [ ] **Schema versioning**: All schemas have `schema_version` field; breaking changes require new version and migration path documented

### 1.3 Feature Pipelines

- [ ] **Volatility features**: Rolling 1h/24h realized vol computed in Flink/streaming job, not by LLM; available on `features.volatility.*`
- [ ] **Regime detection**: HMM or rule-based regime classifier (trending/ranging/volatile) published to `features.regime.*`; agents subscribe, not compute
- [ ] **Trend features**: Moving averages, momentum, RSI computed server-side; LLMs receive trend state (bullish/neutral/bearish), not raw ticks
- [ ] **Crowding/sentiment features**: Aggregated social sentiment score per symbol; funding rate and OI for crypto; short interest for stocks
- [ ] **Implied probability features**: For prediction markets, convert yes/no prices to implied prob and track historical accuracy of market-implied vs actual outcomes
- [ ] **Edge features**: Computed as `(our_prob - market_implied_prob) * stake_size`; only positive-edge opportunities surfaced to agents

## 2. Agent & Model Layer

### 2.1 Specialized Agents per Domain

- [ ] **Crypto agents**: Trend-follower, mean-reversion, funding arb, market-maker, on-chain whale tracker—each with manifest defining role/tools/constraints
- [ ] **Stock agents**: Factor model (value/momentum/quality), news-driven, sector rotation—each constrained to equity universe
- [ ] **Prediction market agents**: Probability estimator (per category: politics, sports, crypto), odds/edge calculator, liquidity assessor
- [ ] **Cross-domain agents**: Risk manager (global), governance agent (kill switch), portfolio allocator (domain weighting)
- [ ] **Agent registry**: All agents registered with `AgentManifest` specifying `role`, `allowed_tools`, `permissions`, `max_position_usd`, `domains[]`

### 2.2 Appropriate Model Types

- [ ] **Numeric models for predictions**: Time-series (ARIMA/Prophet), gradient boosting (XGBoost/LightGBM), or linear models for price/probability forecasting—not LLMs
- [ ] **LLMs for coordination**: Orchestrator uses LLM to interpret agent outputs, explain decisions, select strategies—never to generate prices or probabilities
- [ ] **LLMs for explanation**: All trade/bet decisions have human-readable rationale generated by LLM summarizing agent consensus—stored for audit
- [ ] **No LLM direct execution**: LLM outputs are validated against JSON schema; execution service (not LLM) signs and submits orders
- [ ] **Model inventory**: Each numeric model documented with training data, validation metrics, last retrain date, owner

### 2.3 Strict JSON Contracts

- [ ] **Agent opinion contract**: `{agent_id, symbol, direction, predicted_prob, expected_value, confidence, recommended_action, rationale}`
- [ ] **Recommended action contract**: `{side, size, time_in_force, max_slippage, urgency, domain}`—validated before execution
- [ ] **Prediction market bet contract**: `{contract_id, side (yes/no), our_prob, market_prob, edge, kelly_fraction, max_stake}`
- [ ] **Schema validation**: All agent outputs pass `jsonschema` validation; invalid outputs rejected and logged; 3 failures → agent safe-mode
- [ ] **Forbidden content filter**: Outputs checked for prompt injection, off-topic content, or attempts to exceed permissions

## 3. Swarm Coordination & Risk Controls

### 3.1 Consensus Mechanisms

- [ ] **Per-domain voting**: Crypto agents vote among themselves; stock agents separately; prediction agents separately—each domain has quorum threshold (e.g., 3/5)
- [ ] **Weighted voting**: Agent votes weighted by recent accuracy (rolling 30-day hit rate); poor performers down-weighted
- [ ] **No consensus → no trade**: If domain fails to reach quorum or confidence < threshold (e.g., 60%), no position taken; logged as "abstain"
- [ ] **Veto power**: Risk agent can veto any consensus decision; governance agent can trigger global halt
- [ ] **Consensus audit trail**: Every round logged with votes, weights, final decision, and timestamp for replay

### 3.2 Diversification Rules

- [ ] **Domain allocation caps**: No single domain (crypto/stocks/betting) can exceed 50% of total portfolio risk
- [ ] **Model concentration limit**: No single agent's positions can exceed 20% of domain allocation
- [ ] **Correlation check**: Before adding position, check correlation with existing portfolio; reject if marginal correlation > 0.7
- [ ] **Event clustering**: For prediction markets, limit exposure to correlated events (e.g., multiple political outcomes)
- [ ] **Rebalancing trigger**: If domain weights drift >10% from target, rebalance within 24h or flag for manual review

### 3.3 Hard Risk Controls

- [ ] **Per-agent limits**: Each agent has `max_position_usd`, `max_daily_loss_usd`, `max_leverage` in manifest; enforced pre-trade
- [ ] **Per-domain limits**: Global limits per domain (e.g., crypto max $50k exposure, stocks max $30k, betting max $10k)
- [ ] **Global limits**: Total portfolio `max_drawdown` (e.g., 10%), `max_daily_loss` (e.g., 5%), `max_leverage` (e.g., 2x)
- [ ] **Slippage check**: Orders rejected if estimated slippage > 1% (configurable per asset class)
- [ ] **Price collar**: Orders rejected if limit price >5% away from mid; market orders require explicit override
- [ ] **Kill switch**: Single-click global halt; requires confirmation code to reset; all open orders cancelled, new orders blocked
- [ ] **Circuit breakers**: Per-symbol circuit breaker trips on >10% move in 5min; auto-pause trading that symbol for 15min

## 4. Prediction-/Betting-Market Specifics

### 4.1 Contract Metadata

- [ ] **Resolution conditions**: Each contract has `resolution_source`, `resolution_criteria`, `resolution_deadline` stored; agents must check before betting
- [ ] **Data source verification**: Resolution data sources validated (e.g., AP for elections, official league for sports); no single-source contracts without manual review
- [ ] **Expiry tracking**: Contracts approaching expiry (<24h) flagged; agents cannot open new positions within configurable window (e.g., 2h)
- [ ] **Max loss per contract**: Hard limit on stake per contract (e.g., 2% of betting bankroll); enforced by RiskGuard
- [ ] **Contract lifecycle**: Track contract from discovery → active → trading → settlement → reconciled

### 4.2 Edge Computation

- [ ] **Our probability estimate**: Generated by prediction agents (ensemble or specialized model); stored with confidence interval
- [ ] **Market implied probability**: Computed from yes/no prices accounting for vig/spread; updated in real-time
- [ ] **Edge calculation**: `edge = our_prob - market_prob`; only bet if edge > min_edge (e.g., 5%) AND confidence > threshold (e.g., 70%)
- [ ] **Liquidity check**: Before betting, verify contract has sufficient liquidity (e.g., >$1k available at price); reject thin markets
- [ ] **Expected value**: `EV = (our_prob * win_amount) - ((1 - our_prob) * stake)`; only positive EV bets allowed
- [ ] **Edge decay**: If market moves against us (edge shrinks), auto-reduce or exit position

### 4.3 Bankroll Management

- [ ] **Kelly criterion**: Bet sizing uses Kelly or fractional Kelly (e.g., 0.25x Kelly) to balance growth vs ruin risk
- [ ] **Bankroll segregation**: Betting bankroll tracked separately from trading capital; losses don't cross-contaminate
- [ ] **Max bet as % of bankroll**: No single bet > 5% of betting bankroll; enforced pre-bet
- [ ] **Ruin probability monitoring**: Track probability of ruin given current positions; alert if >1%
- [ ] **Drawdown-based scaling**: If betting bankroll down >20%, reduce bet sizes by 50% until recovery

## 5. Monitoring, Evaluation & Model Risk

### 5.1 Metrics per Domain

- [ ] **Prediction accuracy**: Track directional accuracy (% correct) per agent and domain; dashboard updated daily
- [ ] **Calibration (Brier score)**: Compute Brier score for probability predictions; alert if weekly Brier > 0.25 (poorly calibrated)
- [ ] **Log-loss**: For prediction markets, track log-loss vs market baseline; flag agents worse than market
- [ ] **Latency metrics**: End-to-end latency from signal to order; p50/p95/p99 per domain; alert if p99 > SLA (e.g., 500ms crypto, 2s stocks)
- [ ] **Benchmark comparison**: Compare agent returns to buy-and-hold, market index, and naive strategies; require positive alpha over 30-day rolling
- [ ] **Hit rate by confidence**: Track accuracy stratified by confidence bucket (60-70%, 70-80%, etc.); verify higher confidence → higher accuracy

### 5.2 Model Risk Framework

- [ ] **Model inventory**: All numeric models registered with: name, version, training data dates, features, validation metrics, owner, last review date
- [ ] **Validation status**: Each model has status (approved/provisional/deprecated); only approved models in production
- [ ] **Change management**: Model changes require: documented rationale, backtest results, shadow-mode period, approval before production
- [ ] **Periodic review**: All models reviewed quarterly; review includes performance check, data drift check, and relevance assessment
- [ ] **Retirement process**: Deprecated models have sunset date; auto-disabled after sunset; data retained for audit

### 5.3 Drift and Anomaly Detection

- [ ] **Data drift monitoring**: Track feature distributions vs training baseline; alert if KL divergence > threshold
- [ ] **Prediction drift**: Monitor agent output distributions; alert if mean/std deviate >2σ from 30-day baseline
- [ ] **Anomaly detection on outputs**: Flag outputs that are outliers (e.g., 100% confidence, extreme position sizes)
- [ ] **Safe-mode behavior**: On drift alert, affected agent enters safe-mode (no new positions, existing positions held or reduced)
- [ ] **Automatic rollback**: If new model version causes >X% performance drop in shadow mode, auto-rollback to previous version

## 6. Governance, Compliance & Documentation

### 6.1 Separation of Duties

- [ ] **Agents propose, services execute**: Agents output recommendations; separate execution service validates and signs orders
- [ ] **No LLM signing power**: LLMs cannot access API keys or signing credentials; `SecretsManager` restricts access to execution services only
- [ ] **Human-in-the-loop for large bets**: Positions > $X or bets > Y% of bankroll require human approval (configurable)
- [ ] **Audit trail**: Every decision logged with: agent opinions, consensus result, risk check result, execution status, timestamps
- [ ] **Role-based access**: Operators can pause/resume; admins can change limits; only designated accounts can trigger kill switch

### 6.2 Compliance Considerations

- [ ] **Prediction market jurisdiction**: Kalshi (US-compliant) for real trading; non-US platforms (Polymarket) for paper/simulation only
- [ ] **Securities vs betting classification**: Document which markets are regulated securities (stocks, some crypto) vs prediction/betting; apply appropriate rules
- [ ] **KYC/AML**: User accounts verified per platform requirements; no anonymous trading in regulated venues
- [ ] **Data handling**: PII and trading data stored securely; retention policies documented; no training on customer data without consent
- [ ] **Jurisdictional limits**: Geo-blocking or position limits for users in restricted jurisdictions
- [ ] **Tax reporting**: Generate reports for realized gains/losses per domain for tax compliance

### 6.3 Documentation

- [ ] **Architecture diagram**: Up-to-date diagram showing data flow from feeds → features → agents → consensus → execution → audit
- [ ] **Data schemas**: All schemas documented in `schemas/` with field descriptions, types, and examples
- [ ] **Agent specs**: Each agent has doc with: purpose, inputs, outputs, model type, training data, performance benchmarks
- [ ] **Risk policies**: Document with all risk limits (per-agent, per-domain, global) and rationale; reviewed quarterly
- [ ] **Runbooks**: Operational runbooks for: kill switch activation, agent failure, feed outage, drift alert, model rollback
- [ ] **Onboarding guide**: How to add a new market/domain: required schemas, agent template, risk limits, compliance checklist
- [ ] **Change log**: All production changes logged with date, author, description, and rollback plan
